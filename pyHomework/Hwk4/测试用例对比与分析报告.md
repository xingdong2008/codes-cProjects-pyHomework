### 四、当前代码缺少的防护措施分析 / 4. Missing Safeguards in the Current Code

- **1. 缺少输入类型转换的异常捕获防护 / Missing exception handling for input conversion**：代码 `year = int(input("请输入年份："))` 没有任何 `try-except` 机制。当用户输入字母、空值、复数（1+i）或带小数的数字时，会直接抛出 `ValueError` 并导致程序崩溃，用户体验极差。应增加异常捕获并输出友好提示。
  / `year = int(input("请输入年份："))` has no `try-except`. Letters, empty input, complex numbers (1+i), or decimals raise `ValueError` and crash the program — a poor user experience. Add exception handling with a friendly message.
- **2. 缺少业务逻辑范围校验防护 / Missing business range validation**：代码没有对 `year` 的有效范围进行限制。对于 0 和负数（如 -100），代码依然按照数学公式计算出“是闰年”。在公元纪年体系中，没有公元 0 年，负数年份也无实际意义，应增加 `year > 0` 的校验。
  / The code doesn't restrict `year`. For 0 and negative values (e.g., -100), it still computes "leap year" from the math. In the Gregorian system there is no year 0 and negative years are meaningless; add a `year > 0` check.
- **3. 缺少输入数据清洗防护 / Missing input cleaning**：如果用户在输入前后输入了空格（如 `" 2024 "`），直接使用 `int()` 依然会导致崩溃。应该增加 `strip()` 方法去除首尾空白字符后再进行转换。
  / If the user types spaces around the value (e.g., `" 2024 "`), `int()` still crashes. Add `.strip()` to remove surrounding whitespace before converting.
- **4. 缺少对特定世纪年份的逻辑校验加固 / Missing hardening for century years**：虽然代码逻辑在数学上能正确处理 1900（非闰年）和 2000（闰年），但测试用例反映出对 1900 的处理可能存在误解或遗漏。在业务代码中，应增加针对世纪年（能被 100 整除的年份）的特殊判断分支或注释，以确保逻辑的严谨性。
  / The math correctly handles 1900 (non-leap) and 2000 (leap), but the test cases suggest 1900 may be misunderstood or overlooked. In production code, add an explicit branch or comment for century years (divisible by 100) to make the logic rigorous.
